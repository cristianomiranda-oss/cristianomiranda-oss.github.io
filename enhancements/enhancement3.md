Enhancement Three work performed on artifact from CS-360 Mobile Architect and Programming.

## [Github Repository](https://github.com/cristianomiranda-oss/weight-tracker/tree/enhancement3)

## Origin of the Artifact

One of the main features of any application is generating data based on user actions, and in most cases, the application stores this data for later use. A past artifact in which storing various user data was an essential aspect of the project was my final project for the CS-360 Architect & Programming course. For this project, a weight tracker mobile application was created that allowed users to record their weight data, set and track a goal weight, and finally, have this information tied to the user via a user account. All three major aspects of the process involve creating user data in some manner, whether through the collection of weight values or a username and password, so storing this data in a persistent and easy-to-access manner was essential. The decision to utilize a database was clear since it excels at storing and managing data, and integrating a database with a mobile application was also an easy process. For the initial artifact, SQLite was utilized. This SQL-based database served its purpose and allowed for the creation of different tables: a user account, weight entry, and goal weight entry table, and for entries to easily be created, read, updated, and removed from said tables through controls found within the project's user interface. Still, even though the database and its associated aspects were functional, there were plenty of improvements and changes that could be made to elevate the project further. One of the biggest caveats of the artifact was its limitation to a user's device, so if the user loses the device or clears the mobile application's information, the data they collected and stored will be inaccessible across different devices and lost if the latter instance occurs. In the end, my final project from the CS-360 Mobile Architect & Programming course is a good example of a project that relies on and properly integrates a database and its necessary features, but it can still easily be improved upon to elevate the project further.

## Work Performed

Using the same artifact through all enhancements has allowed for continuous improvement to all aspects of the initial artifact. The first enhancement focused on transferring the mobile application to a web application and updating previous features that were either cut down for time or fixed issues that were previously overlooked. The second enhancement further focused on improving the initial artifact by adding more features and better security using various algorithms, along with improving efficiency through updating how certain data structures were handled. Continuing this pattern, the third enhancement's category is database, and there were plenty of improvements that could be made with the change from a mobile application to a web application. While a previous enhancement did change the database management software, with the change involving the move to Indexed DB from SQLite as the former is already built into most modern web browsers, it still retained many of the shortcomings of the original database from the initial artifact. The biggest issue with the current approach is the limitation of data storage, as it is limited to a single device, so attempting to use the application from other devices would result in no previous data being available to a user. Thus, the focus for this enhancement was to switch to a cloud-stored database that retained similar characteristics to Indexed DB, the biggest being the ability to store JSON objects, and the best fit was MongoDB. For this enhancement, MongoDB Atlas was used to initialize a database and allow the project to connect to it to perform the necessary CRUD operations, which finally allows data to be stored in the cloud and persist across any device. The major work performed on this enhancement was in the database and server components, as this change required recreating the database and reworking the existing database access logic to support accessing the cloud MongoDB database. This inclusion of persistent data across multiple devices can still be improved by allowing the data to be accessible beyond the current web application. This feature was accomplished by making the various database CRUD methods accessible through API endpoints. By making these endpoints available, other programmers can build different front-end applications, such as a desktop application or a mobile application, that use these endpoints to perform any CRUD operations on the existing MongoDB database, allowing data to persist regardless of how a user accesses the application.
![A data flow diagram that details the movement and storing data within the web application.](../assets/Weight%20Tracker%20Data%20Flow%20Diagram.png)

The above data flow diagram shows how this consistency is maintained regardless of how a user accesses the database, whether through the front-end web application or the added API endpoints. The diagram shows how data travels through specific processes before being stored in the database or retrieved from it. The key detail is that, regardless of how the user accesses data, the processes remain the same. This ensures that even external applications that use the API endpoints still undergo the same data validation and security checks before being allowed access to the database, maintaining consistency for user data and user security. The last major improvement was adding additional security features beyond relying on middleware to securely access the database from the application backend. Including accounts with varying roles for the database ensured the principle of least privilege was followed when accessing the database. Limiting a user to reading and writing on specific collections ensures they cannot perform administrative actions and can only access the collections defined for the project. Overall, the third enhancement mainly focused on improving the current database by switching to a cloud-stored database to make data persistent across multiple devices, make the database accessible to other programmers in their projects, and improve security to ensure the API endpoints do not add any vulnerabilities to the existing project.

## Enhancement Outcomes

In this enhancement, the focus was on achieving the first course outcome, the creation of a collaborative environment. While other outcomes were achieved as well, the second, which encourages the proper creation of documentation, and the fifth, the focus on handling security vulnerabilities within the project, both helped to achieve the first course outcome. A collaborative environment requires other programmers to understand how an application was created by providing details on how the approach to solving problems was performed, and that working with this application can be done securely. Thus, the creation of the collaborative environment through the change to a cloud-stored database, the decision to use a non-administrative account, and finally, the inclusion of API endpoints so that the database can be interacted with through other projects all serve to create a collaborative environment where other programmers can work on or utilize the project to allow user data to remain consistent in their projects as well. In the end, the initial plan was to mainly satisfy the first course outcome, which inevitably resulted in the satisfaction of other course outcomes, but the initial goal was still achieved through the work performed on enhancement three.

## Takeaways

Working on this enhancement resulted in me completing my first application in which data is stored persistently across multiple devices. Finally having the chance to integrate a cloud-stored database allowed me to gain real experience with connecting to and managing a database stored in the cloud, which is how nearly every business's web applications function. The process itself was not entirely challenging, as connecting to the MongoDB database and setting up the various CRUD methods is a process I have performed before, albeit with a locally hosted database. However, the challenge presented itself in understanding that relying on a cloud-stored database and storing potentially sensitive user data on it was a major responsibility. Thus, my focus for this change was not only on correctly integrating the database into the existing CRUD methods but also on doing my due diligence and researching potential vulnerabilities or exploits that could occur. Properly handling any exploits or vulnerabilities and correctly implementing solutions to prevent them from occurring was a necessary step of the process and one that proved to be difficult, as there were a lot of potential issues that could occur; but regardless of the time and effort needed, it proved to be worth it in the end. My biggest takeaway from this work was that creating a secure and functional application takes time, and attempting to take shortcuts or overlook specific issues would result in far greater consequences that outweigh any time saved. By far, the research and development that went into properly securing the database connection and CRUD methods was the most challenging aspect of the project, but it also proved to be the most worthwhile as it helps ensure that any known exploit is properly handled and user data is better protected.
